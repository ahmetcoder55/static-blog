Clean Architecture

Veri tabanı, UI ve dış bağımlılıklardan tamamen soyutlanmış, test edilebilir ve sürdürülebilir sistemler inşa etmek.

🛡️ Uncle Bob Standardı & Domain-Centric
📅 8 Eylül 2026 | ✍️ Yazar: Ahmet | ⏱️ Okuma Süresi: 12 dk

Giriş: Yazılımlar Neden Çürür (Software Rot)?

Bir proje ilk başladığında her şey harikadır. Kodlar hızlıca yazılır, veritabanı bağlantıları doğrudan controller veya servis sınıflarına gömülür ve ürün yayına alınır. Ancak proje büyüdükçe, iş kuralları (Business Rules) geliştikçe ve müşteri yeni isteklerle geldikçe sistem spagetti koda dönüşür. Küçük bir değişiklik, projenin hiç alakası olmayan bir yerini patlatmaya başlar.

Robert C. Martin (Uncle Bob) tarafından ortaya konan Clean Architecture (Temiz Mimari), bu çürümeyi engellemek için geliştirilmiştir. Temel parolası şudur: "Yazılım mimariniz, kullandığınız veritabanı, web çatısı (framework) veya kullanıcı arayüzü (UI) hakkında hiçbir fikir sahibi olmamalıdır."

1. Altın Kural: Bağımlılık Kuralı (The Dependency Rule)

Clean Architecture mimarisinin kalbinde tek bir kırılmaz kural yatar: Koddaki bağımlılıklar sadece ve sadece içe doğru yönelebilir.

Dış katmanlar iç katmanları tanıyabilir, ancak iç katmanlar dış katmanlardaki hiçbir şeyden haber dar olamaz. Yani iş mantığınızın (Domain), kullandığınız veritabanının Entity Framework mu yoksa PostgreSQL mi olduğundan ya da projenin React mi yoksa ASP.NET Core MVC mi kullandığından haberi yoktur.

📌 Unutmayın: Veri tabanı bir detaydır. UI bir detaydır. Dış servisler (Sms, Mail, Ödeme Sistemleri) birer detaydır. Temiz bir mimaride detaylar iş kurallarına bağımlı olur, iş kuralları detaylara değil!

2. Clean Architecture Katmanları

Mimari, iç içe geçmiş halkalar gibi düşünülür. Dışarıdan içeriye doğru 4 ana katmandan oluşur:

1. Domain Layer (En İç Katman - Çekirdek)

Projenin kalbidir. Hiçbir dış kütüphaneye veya framework'e bağımlılığı yoktur (Pure C#). Şunları barındırır:

  • Entities: İş nesneleri ve veritabanı tablolarının karşılıkları.
  • Value Objects: Kendi kimliği olmayan ama değer ifade eden yapılar (Örn: Adres, Para Birimi).
  • Enums & Constants: Proje genelinde kullanılan sabitler.
  • Domain Events: İş alanında gerçekleşen önemli olaylar.

2. Application Layer (Uygulama Mantığı)

Sistemin kullanım senaryolarını (Use Cases) barındırır. Domain katmanını kullanır ancak UI veya DB'den habersizdir:

  • Interfaces: Veritabanı (Repository) ve Dış Servis (Email, SMS) arayüzleri.
  • CQRS (Commands & Queries): MediatR ile işlenen komut ve sorgu işleyicileri.
  • DTOs & Mapping: Veri transfer nesneleri ve AutoMapper/Mapster profilleri.
  • Validation Rules: FluentValidation ile girdi doğrulama kuralları.

3. Infrastructure Layer (Altyapı Katmanı)

Application katmanında tanımlanan arayüzlerin (Interface) somutlaştırıldığı (Implementation) yerdir:

  • Persistence (Database): EF Core DbContext, Migration'lar ve Repository sınıfları.
  • External Services: JWT Token üretimi, Mail gönderme servisleri, PayTR/Stripe entegrasyonları.
  • System Clock & Logging: Dosya sistemine erişim ve loglama mekanizmaları.

4. Presentation / Web API Layer (En Dış Katman)

Kullanıcının veya dış sistemlerin projeyle temas ettiği noktadır:

  • Controllers / Minimal APIs: İstekleri karşılar ve MediatR aracılığıyla Application katmanına iletir.
  • Middlewares: Küresel hata yönetimi (Global Exception Handling), Rate Limiting.
  • Configuration: Program.cs, Dependency Injection konfigürasyonları.

3. Kod Üzerinde Görelim: Bir Ürün Ekleme Akışı

Bir ürünü sisteme kaydetme senaryosunu Clean Architecture ilkelerine göre nasıl kodladığımıza adım adım bakalım:

Adım A: Domain Katmanında Entity Tasarımı
namespace CleanArch.Domain.Entities;

public class Product
{
    public int Id { get; private set; }
    public string Name { get; private set; } = string.Empty;
    public decimal Price { get; private set; }

    // Domain kuralı: Ürün fiyatı sıfırdan küçük olamaz
    public Product(string name, decimal price)
    {
        if (price <= 0)
            throw new ArgumentException("Ürün fiyatı 0'dan büyük olmalıdır.");

        Name = name;
        Price = price;
    }
}
Adım B: Application Katmanında Interface ve CQRS Command
namespace CleanArch.Application.Abstracts;

// Application katmanı veritabanının EF Core olduğunu bilmez, sadece interface tanımlar
public interface IProductRepository
{
    Task AddAsync(Product product, CancellationToken cancellationToken);
    Task<Product?> GetByIdAsync(int id, CancellationToken cancellationToken);
}

// CQRS Command Yapısı (MediatR)
public record CreateProductCommand(string Name, decimal Price) : IRequest<int>;

public class CreateProductCommandHandler : IRequestHandler<CreateProductCommand, int>
{
    private readonly IProductRepository _repository;

    public CreateProductCommandHandler(IProductRepository repository)
    {
        _repository = repository;
    }

    public async Task<int> Handle(CreateProductCommand request, CancellationToken cancellationToken)
    {
        var product = new Product(request.Name, request.Price);
        await _repository.AddAsync(product, cancellationToken);
        return product.Id;
    }
}
Adım C: Infrastructure Katmanında EF Core İle Somutlaştırma
namespace CleanArch.Infrastructure.Persistence.Repositories;

public class ProductRepository : IProductRepository
{
    private readonly ApplicationDbContext _context;

    public ProductRepository(ApplicationDbContext context)
    {
        _context = context;
    }

    public async Task AddAsync(Product product, CancellationToken cancellationToken)
    {
        await _context.Products.AddAsync(product, cancellationToken);
        await _context.SaveChangesAsync(cancellationToken);
    }

    public async Task<Product?> GetByIdAsync(int id, CancellationToken cancellationToken)
    {
        return await _context.Products.FindAsync(new object[] { id }, cancellationToken);
    }
}
Adım D: Presentation Katmanında Web API Controller
[ApiController]
[Route("api/[controller]")]
public class ProductsController : ControllerBase
{
    private readonly IMediator _mediator;

    public ProductsController(IMediator mediator)
    {
        _mediator = mediator;
    }

    [HttpPost]
    public async Task<IActionResult> Create([FromBody] CreateProductCommand command)
    {
        var productId = await _mediator.Send(command);
        return CreatedAtAction(nameof(GetById), new { id = productId }, productId);
    }
}

4. Siber Güvenlik ve Test Edilebilirlik Açısından Avantajları

Clean Architecture sadece mimari bir şov değildir. Yazılıma çok somut iki devasa güç kazandırır:

🧪 Kolay Unit Test (Moq)

Application ve Domain katmanları dış dünyadan tamamen izole olduğu için, veritabanına bağlanmadan sahte verilerle (Mocking) milisaniyeler içinde binlerce Unit Test çalıştırabilirsiniz.

🛡️ İzole Güvenlik Duvarı

API katmanına gelebilecek bir DDoS veya SQL Injection atağı, iş kurallarınızın bulunduğu çekirdeğe ulaşamaz. Güvenlik katmanları (Validation, Auth) altyapıdan bağımsız taranabilir.

Sonuç

Clean Architecture küçük projeler için ilk başta "over-engineering" (gereksiz fazla mühendislik) gibi görünebilir. Ancak orta ve büyük ölçekli, zamanla büyüyecek kurumsal projelerde yazılımın ömrünü uzatan, geliştirici maliyetini düşüren ve spagetti kod oluşumunu kesin olarak engelleyen en güçlü mimari çözümdür.
